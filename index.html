Pipeline & Test Report

Testing the best LLM/VLM combinations for document data extraction.

Test Plan

The main focus of testing on this project is document conversion accuracy across different OCR/LLM pipelines. API and UI testing cover the surrounding application.

Scope

In scope: extraction accuracy across OCR/LLM pipeline combinations, the document-job API surface, and core UI flows (settings, language, schema, providers).

Out of scope for this round: load/performance testing, security testing, and batch-folder regression testing.

Approach

Pipeline accuracy is benchmarked by running each OCR/LLM combination against the same hand-labeled invoice set and scoring field-level output. The API surface is checked with direct HTTP requests against a running backend. UI flows are covered with Playwright, split into standalone specs (mocked, fast, no live provider) and integration specs (real provider, real document, opt-in with RUN_INTEGRATION=true).

Environment & tools

Local LM Studio models and the GLM 5.2 cloud API as extraction backends; Google Vision API and a local Qwen3-VL model as OCR options; Playwright for browser automation; direct HTTP calls for API checks; a hand-labeled set of invoices as ground truth for scoring.

Exit criteria

A pipeline combination is considered viable once it clears 85% field-level accuracy with zero missing documents on the test set. API and UI specs must pass with zero known failures before being counted as covered.

Benchmarks

Six extraction models, three OCR strategies, run against the same set of 14 Estonian/Russian invoices.

OCR Comparison: Google Vision vs. Local VLM

The two OCR strategies tested fail in complementary, opposite ways — one gets the characters right but misplaces lines, the other keeps structure intact but introduces small character errors.

Google Vision

✓ Near-perfect character accuracy
  • Best raw text recognition of the OCR engines tested — individual characters and words come through cleanly.
  • Strong on dense, well-printed source documents.
✕ Unreliable spatial reconstruction
  • Stray lines can land in the wrong position in the reconstructed text — a line from the header block can surface in the middle of an item list, or vice versa.
  • Three reconstruction modes were tried, covered below — none fully solved it. Plain paragraph mode ended up the best trade-off.

Local VLM (Qwen3-VL)

✓ Preserves document structure
  • Line order and grouping stay much closer to the original layout — item rows, header blocks, and totals stay where they belong.
  • Produces output the LLM can parse more predictably, with no need for coordinate metadata.
✕ Character-level noise
  • Introduces roughly 1–3 small errors per run — typically duplicated letters or stray spaces.
  • The 30B variant was also tested against the 8B model specifically to see if more parameters reduced this noise — the difference was minimal. Both sizes produce similar text errors, in either direction.

Google Vision reconstruction modes tried

  • Paragraph mode — the best of the three. Some column bleeding still occurs, but the document stays mostly usable for the LLM.
  • Plain/flat text mode — same line-placement issue as paragraph mode, no real improvement.
  • Y-block / single-line-per-row mode — reconstructed each row as one long line spanning the full page width. This did fix the stray-line problem, but introduced a worse one: words split across two source rows would lose their context entirely, and a single reconstructed line could end up containing two unrelated addresses merged together. This was the worst result of the three and was never committed to the pipeline.

Conclusion & Summary

Where the project stands after benchmarking six models across three OCR strategies.

On the OCR side, Google Vision and the local VLM fail in complementary ways: Google Vision has near-perfect character accuracy but unreliable spatial reconstruction, while the local VLM preserves document structure well but introduces small character-level errors. Paragraph-mode Google Vision ended up the best practical balance after testing flat text and a Y-block single-line reconstruction, the latter of which fixed stray lines but caused worse problems — split words losing context and unrelated addresses merging onto one line.

Across the pipeline combinations tested, the same pattern holds at the model level: Google Vision feeding an LLM is generally stronger on raw accuracy, while VLM-based OCR and single-stage (no-OCR) vision pipelines are generally stronger on structure — keeping item rows, header fields, and totals correctly grouped. Neither approach dominates outright; the best results came from pairing local VLM OCR with a strong cloud model (GLM 5.2), suggesting the cleaner structure from local OCR matters more to final accuracy than the small character noise it introduces.

Schema complexity turned out to matter more than expected. Simpler schemas consistently performed better — fields that can be calculated from other already-extracted fields (totals, sums, derived amounts) should be computed after extraction rather than asked of the model directly, since asking for them adds room for error without adding real information. This connects to a broader attention issue seen early in testing: asking a single VLM to both read a dense, multi-section document and produce well-formed JSON in one pass is a harder task than splitting OCR and extraction into two stages, which is part of why two-stage pipelines tend to be more reliable than asking one vision model to do both jobs at once.

The clearest next step is a validation layer rather than a model change — checking extracted addresses against an address database and extracted company names against a company registry, the same way the existing counterparty table could be used for fuzzy matching. Item-level extraction is already in good shape: item counts and line-item accuracy are usually reliable, so validation effort is better spent on the header-level fields (seller, address) where OCR-driven errors actually concentrate.
